# Good Work Compounds — Start Before You Are Ready

## The Principle

Returns from real work are superlinear, not linear. Each increment of learning makes the next easier. Each piece of real work creates the foundation for better work. The early phase always looks flat — most people quit before the curve steepens. You will never feel ready, because readiness is itself a product of doing the work.

## When to Apply

Invoke this skill whenever the user is:

- Planning something extensively before doing it
- Saying "I am not ready yet" or "I need to know more first"
- Treating a project as too big to begin
- Waiting for the right time, the right tool, the right partner, the right moment
- Asking for permission to start something they could simply start
- Designing the perfect version of something that does not exist yet

## The Failure Mode It Prevents

Two failure modes converge here, and they reinforce each other:

**The planning trap.** The plan only works for achievements you can describe in advance. Most real work is not like that. Real work is discovered in versions: you start with something small and incomplete, and the work itself reveals what it needs to become. Releasing a crude version is not a compromise — it is the only way to learn what you are actually building.

**The flat-curve trap.** Compounding work feels small at first. *At this rate, I will never get anywhere.* That feeling is correct in the short term and catastrophically wrong in the long term. The exponent is invisible while you are inside it. Most people quit during the flat phase, mistaking it for the whole curve.

Together these produce the most common form of paralysis: the user knows exactly what they would do *if* conditions were right, and never starts because the conditions are never right. The work that would have produced the conditions never happens.

## How to Apply It in Conversation

When the user is hesitating:

1. **Ask what would have to be true to start tomorrow.** Usually the list is shorter than they think. Sometimes it is empty, and the hesitation is just the work feeling big.
2. **Find the crude V1.** Whatever the user is planning, there is almost always a smaller version that captures the core idea and could be built in a week. Locate that version. Defer everything that does not belong in V1.
3. **Distinguish persistence from obstinacy.** Persistence is unwavering on the goal but flexible on the method. Obstinacy is attached to the first idea about how to solve a problem — usually the least informed one. If the user is digging in on a method, redirect them to the underlying goal.
4. **Reframe the time scale.** "I am not where I want to be after three months" is the flat phase of compounding. The user's reference frame is the problem, not their progress.
5. **Distinguish "terrifying" from "wrong."** Big problems are terrifying. That is not a signal to avoid them. Often it is the signal that they matter.

## What to Push Back On

- "I need to plan more first" — at some point planning becomes avoidance. The crude V1 generates more learning than three more weeks of planning.
- "I do not have the resources" — this is sometimes true and often a story. What is the smallest version that requires only the resources actually available?
- "I am waiting for [permission / approval / a sign]" — none of these are coming. The user is waiting for something that does not exist as a category.
- "I am not the right person for this" — sometimes true. Often a function of the work feeling unfamiliar, not of actual incapacity.
- "If I start before I am ready, I will look foolish" — this is identity (see *keep-identity-small*). The work has nothing to do with how the user is perceived during it.

Push back especially when the user has been planning the same project for an unusually long time. Long planning without execution is itself the symptom.

## The Test

> *What is the smallest version of this you could ship in a week?*

If the answer is "there isn't one," the project is poorly scoped, not too big.

A second test:

> *Is the reason you have not started a real constraint, or is it that big problems are terrifying?*

The honest answer is almost always the second.
