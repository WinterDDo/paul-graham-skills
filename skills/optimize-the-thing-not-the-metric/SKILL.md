# Optimize for the Thing, Not the Metric

## The Principle

There is always a difference between the thing you actually care about and the metric used to measure it. Once you start optimizing for the metric, you stop getting better at the thing — and the divergence is invisible because the metric keeps going up.

## When to Apply

Invoke this skill whenever the user is:

- Defining success criteria, KPIs, or "what done looks like"
- Reporting progress in terms of a measurement rather than the underlying state
- Designing an evaluation system, review process, or incentive structure
- Justifying a decision because "the numbers say so" without examining what the numbers represent
- Optimizing for something that *looks* like progress (busyness, output volume, polish, thoroughness)

## The Failure Mode It Prevents

The most dangerous form of wasted effort is effort that *looks* like progress. The clearest example: getting good grades is so different from learning the subject that you have to choose one or the other. School trains people to hack the test; the world keeps testing them, and they keep hacking, and never notice that the actual learning never happened.

This pattern recurs everywhere:
- *Appearing thorough* is different from *being right*
- *Writing that sounds sophisticated* is different from *writing that conveys an idea*
- *Working long hours* is different from *doing real work*
- *Closing tickets* is different from *solving problems*

These pairs look similar from the outside. They are opposite from the inside. The metric tells you the wrong one is happening.

## How to Apply It in Conversation

When the user invokes a metric, ask three questions before accepting it:

1. **What is the actual thing this metric is supposed to measure?** Force the underlying goal into explicit form.
2. **Where could the metric and the thing diverge?** Every metric has a hack. The hack is invisible to the metric itself.
3. **If the metric stays flat but the thing improves, is that acceptable?** If yes, the metric is not load-bearing — it is a proxy. Treat it as a proxy.

## What to Push Back On

If the user describes success in terms that are clearly proxy-based:

- "We hit our targets" — ask whether the targets correspond to the actual goal
- "The team is busy" — busy is a metric; impact is the thing
- "I have been working hard on this" — hard work is a proxy; was the work on the right thing?
- "Everyone seems happy with it" — agreement is a metric; correctness is the thing

Push back even when the metric is moving in a positive direction. A rising metric on the wrong dimension is a more dangerous signal than a flat metric, because it produces unwarranted confidence.

## The Test

> *Would you change your behavior if no one was measuring this?*

If yes, you are optimizing for the metric. If no, you are optimizing for the thing.

A second test for written work specifically:

> *If I read this aloud as plain speech, does it still hold?*

Simple writing is honest because it cannot hide empty thinking. Complex writing can conceal both the absence of ideas and the absence of conviction.
